# UAF 1.2 作战场景分析技能

把一个作战场景(装备参数 + 敌我双方 + 作战流程)转化为:一份结构化的分析报告,加一套可在 MagicDraw 2022x(UAF 1.2 插件)中逐步落地的建模方案。工作流提炼自“区域防空”场景的完整分析过程,已验证可复用。

## 适用前提

- 建模工具固定为 MagicDraw 2022x,插件固定为 UAF 1.2。不要推荐其他工具或其他 UAF 版本;用户另有说明时再调整。
- 输出的是分析与建模方案,不是 .mdzip 模型文件。给出的视图清单、元素、关系应能让用户照着在 MagicDraw 里建出来。
- 本技能的视图命名依据 UAF 1.2,但插件实际提供的视图名称以用户安装的版本为准。详见 `references/uaf12-views.md`,其中标出了哪些命名是已核实的、哪些需要用户在软件中核对。**绝不要把未核实的命名当作事实写进报告**。

## 工作流总览

按下列阶段顺序推进。每个阶段有明确产出和一个“闸门”(完成标准),过了闸门再进入下一阶段,这样追溯链不会断。

| 阶段              | 工作                                     | 产出                     | 闸门                              |
| ----------------- | ---------------------------------------- | ------------------------ | --------------------------------- |
| 0 输入核查        | 整理参数、识别歧义与笔误、列出假设       | 参数表、假设与待确认清单 | 阻塞性歧义已确认,其余已写成假设   |
| 1 能力分析(St)    | 从作战流程提炼能力及依赖                 | 能力清单、依赖关系       | 每个流程步骤至少对应一项能力      |
| 2 作战分析(Op)    | 执行者、信息交换、活动、顺序、状态、约束 | Op 各视图内容            | 每个步骤都有活动,每个活动有执行者 |
| 3 服务分析(Sv)    | 把能力封装为服务,定义提供/使用关系       | 服务表                   | 每个服务有提供方和使用方          |
| 4 资源分析(Rs/Ar) | 装备类型、接口、功能、实例与部署         | 资源表、实例表           | 每项活动/服务有资源承担           |
| 5 需求与追溯      | 需求、Satisfy/Verify、各 Tr 视图         | 需求表、追溯矩阵方案     | 无“无资源的活动”“无需求的资源”    |
| 6 效能估算        | 时间窗口、覆盖、链路时延的示例估算       | 估算表(标注假设)         | 所有数值标注来源或“假设”          |
| 7 建模实施方案    | MagicDraw 分步操作、包结构、校验         | 12 步左右的实施清单      | 与前述各阶段视图一一对应          |
| 8 报告成稿        | 按模板组装                               | 分析报告                 | 见下方“交付前自检”                |

各阶段的细则与模板:
- 输入核查清单与歧义识别 → `references/scenario-intake.md`
- UAF 1.2 视图映射与命名核对 → `references/uaf12-views.md`
- 报告章节模板 → `references/report-template.md`
- MagicDraw 实施步骤与校验 → `references/magicdraw-workflow.md`
- 完整范例(区域防空)→ `references/example-regional-air-defense.md`

## 各阶段要点

### 阶段 0:输入核查(最容易出错,先做)

用户给的参数常有口误或量纲问题,直接建模会把错误固化进整份报告。先做三类检查,细则见 `references/scenario-intake.md`:

1. **量纲与量级**:面积、半径、速度是否自洽。例如“500 平方公里”的部署区域与 300 km 探测半径明显不匹配,应当提问,而不是默默采用。
2. **角色与动词**:流程里“谁做了什么”是否合理。例如“雷达击毁敌机”应是导弹击毁、雷达引导,发现后写成假设并告知用户。
3. **缺失参数**:敌机速度、导弹速度、融合时延等。缺失时不要编造为事实,给出示例值并标注“假设”。

提问规则:只问会改变整体结论的阻塞性问题,一次最多一个;其余写进“假设与待确认事项”后继续推进。用户回答后,同步修改所有受影响的章节(参数表、假设、部署、估算),不要只改一处。

### 阶段 1–2:从流程到能力、到活动

- 把作战流程每一步改写成“谁 — 做什么 — 输出什么”,这就是作战活动(OA)的原料。
- 能力(C)是活动的抽象:多个活动可支撑同一能力。能力之间的依赖按信息和决策的先后排列。
- 流程步骤与 OA 保持**显式对照表**(步骤号 → OA → 执行者 → 输出)。这张表是后续追溯的根。
- 并行的步骤(如“持续跟踪”与“打击”同时进行)在活动图里用并行分支表达,不要串成一条线。
- 流程里隐含但未写的分支(如“未击毁则二次打击”)可作为合理补充加入,但必须在报告里说明这是补充。
- 信息交换(IE)逐条编号,写清发送方、接收方、内容。

### 阶段 3–4:服务与资源

- 服务是“能力的可调用形式”,按提供方/使用方列表。
- 资源分两层:**类型**(Rs,如“三坐标相控阵雷达”)和**实例**(Ar,如 Radar-1~3 及其部署坐标、性能参数)。数量、半径、距离等参数放在实例上。
- 若流程提到“配装”“边缘处理”等附属装备,单独建成资源,并说明数量假设(如每台探测设备配 1 套)。

### 阶段 5:追溯

没有追溯,架构模型只是图的集合。至少建立:能力 ↔ 需求,活动 ↔ 能力/需求,服务 ↔ 活动,资源 ↔ 服务/活动/需求,实例 ↔ 类型。完成后用依赖矩阵检查两类缺口:没有资源承担的活动,没有需求支撑的资源。

### 阶段 6:效能估算

只做能用给定参数推出来的估算,例如预警缓冲 = 探测半径 − 导弹远界,可用时间 = 缓冲 ÷ 目标速度。必须写明前提(同址或相近部署、直线接近)和假设值,并说明部署分散时结论会如何变化。给不出的结果就说给不出,不要硬凑。

## 报告写作要求

- 结构见 `references/report-template.md`,章节顺序固定:概述 → 方法与视图规划 → 战略 → 作战 → 服务 → 资源 → 效能估算 → 需求与追溯 → 建模步骤 → 结论。
- 表格优先:能力、活动、信息交换、服务、资源、需求都用表格,便于逐项对照建模。
- 每章用 UAF 视图编号标注内容所属视图(如 Op-Sr、Op-Pr),但**只使用 `references/uaf12-views.md` 中已核实的编号**。
- 假设、待确认、示例数值必须能在报告里一眼找到。

## 交付前自检

逐条核对后再交付:
1. 流程每一步都能在“步骤 → OA”对照表里找到。
2. 每个 OA 有执行者,每个执行者在资源表里有对应资源。
3. 视图编号没有出现 `Op-Tr` 当顺序图、`Rs-Fn`/`Sv-Fn`、独立的 `Rq` 视点这类 UAF 1.2 中不成立的用法。
4. 所有数值要么来自用户输入,要么标了“假设”。
5. 用户已纠正的参数,在全文所有位置都已更新。
6. 对 Sm/Am、人员视点编号等未核实项,已提示用户在软件中核对。

## 与用户沟通

- 用户若指出视图命名与 UAF 1.2 不符,先承认并按其所见的插件实际名称修改,不要辩解。
- 用户要求“按 1.2 修订”这类整体改动时,整体梳理一遍所有章节的视图编号,不要只改被点名的地方。
- 报告应作为可编辑文档交付;在没有文档工具的环境中,交付 Markdown 或 Word 文件。
