# 任务工程（ME）扩展：在 UAF 1.2 中落地“问题 → 线程 → 工程线程 → 度量”

目录:1 何时用 · 2 映射 · 3 八步清单 · 4 与已有视图的去重 · 5 数值与参数代号 · 6 核对第三方方法文档 · 7 本项目的实现状态

## 1 何时用

用户提出“任务工程”“任务线程 MT”“任务工程线程 MET”“MOE/MOP”“基线与替代方案对比”，或给出按 OUSD(R&E) 任务架构样式指南写的方法文档时使用。它是主流程（阶段 0~8）之后的可选扩展，建在已有的能力、活动、资源、追溯之上，不替代它们。

## 2 ME 链条到 UAF 1.2 的映射

| ME 环节 | UAF 视点 | UAF 1.2 的承载方式 |
|---|---|---|
| 问题定义、场景、想定片段 | 战略 St-Tx | `StrategicPhase`（场景组合想定片段） |
| 场景目标与成功准则 | St-Tx | `EnterpriseGoal`，度量写在属性里 |
| 任务线程 MT（解决方案无关） | St-Tx 引出，Op 展开 | 自建 Profile 的 `MissionTask`，隶属一个 `MissionThread`；与作战活动 OA 追溯 |
| 任务工程线程 MET（具体资源） | Rs | 自建 Profile 的 `MissionEngineeringThread`；落到资源、系统功能、资源交换 |
| 度量评估 | 参数 Pm | `MeasurementSet` + `Measurement`，`Typical Measurements Table` |

UAF 1.2 没有 Mission*、ForceDesignation。敌我区分沿用“敌方放外部目标执行者”的做法。

## 3 八步清单（D0~D7）

| 步 | 视图 | 做什么 | 要点 |
|---|---|---|---|
| D0 | — | 固定问题定义、基线与替代方案、修订原则 | 问题先于画图；写明哪些装备在基线里 |
| D1 | St-Tx | 场景、想定、目标、MT、MET 及 Trace | 另起一张 Strategic Taxonomy 图，不与能力分类混放 |
| D2 | Op-Pr | MT 规格 + OA→MT 追溯 | **不另画活动图**，每个 OA 归入一个 MT，数量逐组核对 |
| D3 | Rs-Sr | 资源×MT 覆盖表与缺口分析 | 取自已有资源；表由 RS→功能→OA→MT 推导，通常只放文档 |
| D4 | Rs-Pr | 按想定画资源泳道流程 | 泳道是资源，动作引用已有系统功能；使用规则建成串联升级链 |
| D5 | Rs-Cn | 端到端连接派生图 | 复用已有资源交换，自左向右按阶段排布 |
| D6 | Pm-Me | MOE/MOP/TPM | MOE 对应目标；MOP 取自活动链；TPM 取自装备参数 |
| D7 | Tr | 补 ME 链缺的追溯 + 检查 | 只补缺的，不重做原有 Tr |

## 4 与已有视图的去重（最容易犯的错）

在已有项目上做 ME，先列“已有 / 新增 / 重复”，再动手。

| 第三方文档常见做法 | 与已有模型的关系 | 处理 |
|---|---|---|
| 另画 MT 活动图 | 与 OA 及作战流程图同义 | 只做 OA→MT 追溯和 MT 规格 |
| 另编 R-01~R-07 资产清单 | 与资源类型、实例重复，还常漏装备 | 用已有资源编号，只做覆盖表 |
| 另画 E2E 接口图并另编接口 | 与已有资源交换重复 | 派生图，复用已有交换 |
| 追溯矩阵一整张重做 | 已有 St/Op/Sv/Rs/Ar 追溯 | 只补 ME 链上缺的几段 |

## 5 数值与参数代号

- 场景输入没给的值不编造。目标阈值若取自第三方文档，标为“待确认”假设，并说明来源。
- 新增装备的性能未给出时，用参数代号（如 `P_JAM_R` 干扰作用距离、`P_INT_V` 拦截无人机速度）表示，集中列在报告一节，装备参数确定后替换；MOP 的目标值写“待定”或写表达式（如“约为 P_INT_T + 距离 ÷ P_INT_V”）。
- 时间窗口分析对未给出的装备只做定性判断，并写出代号表达式。
- 使用规则（先软杀伤、再拦截、末道用发射枪等）向用户确认后写成升级链，状态标“已确认”；附带损伤、对己方通信影响等仍未确认的子项继续标待确认。

## 6 核对第三方方法文档的清单

| 检查项 | 说明 |
|---|---|
| 版本 | 文档按 UAF 1.3 写（MissionThread、ForceDesignation 等），本项目是 1.2，要改映射 |
| 装备 | 文档的资产与项目装备是否一致；缺了哪些、多了哪些 |
| 重复 | 是否另造一套已有元素（见第 4 节） |
| 关系方向 | `Satisfy` 的 client 是满足方；`Implements` 连的是功能→作战活动，别用来连任务→资源 |
| 视图名 | 视图名与插件实测是否一致；Pm-Me 在 1.2 是表 |
| 数值 | 有无无出处的数值或外部统计，删除或标待定 |
| 自相矛盾 | 图与表是否对得上（箭头端点、接口数量）；先说度量应早定又放在最后 |
| 内部一致 | MT 在一份文档里是“线程”，另一份里是“任务” |

修订结果写回原文档，并在每个文件开头写“状态”（待实现 / 已实现 / 部分实现）和与原稿的差异表。
